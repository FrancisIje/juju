juju · Phase 7 · Product analytics

Count what people do, from the same SDKs that catch their crashes

Error tracking says what broke. Product analytics says what people do: how many started a checkout, how many finished it, and how many came back. Phase 7 adds capture, identify and reset to the web, React Native and Flutter SDKs, stores the events in ClickHouse, and adds trends, funnels and retention to the dashboard.

Analytics events travel the same path as errors up to ingest: the same SDK queue (batching, retry with backoff, saved across app restarts), the same envelope and endpoint, the same key check. Ingest then puts them in their own durable queue. A writer reads that queue and inserts into ClickHouse in batches, at most once a second.

Why ClickHouse, not PostgresAnalytics events outnumber errors by 100× or more, and the questions are always "count these over time, grouped by that". ClickHouse stores each column separately and compressed, so a trend reads only the timestamp, name and breakdown columns. Postgres reads whole rows. Postgres still keeps everything else: users, projects, issues.
Why analytics is optionalWithout JUJU_CLICKHOUSE_URL, juju works exactly as before and the Analytics page says how to turn it on. Nobody should need a second database to track crashes, and if ClickHouse goes down, errors keep flowing: analytics events wait on disk and are written once it's back.
Decisions

What makes the numbers right

One person before and after login

Each device gets a random anonymous id (stored in localStorage, AsyncStorage, or a file). identify("user_42") after login sends one link, anonymous id → user, and later events carry the user id. Queries resolve every event through those links, so a person who browsed anonymously and then bought something counts once. In the run, the web example sent 3 checkouts, 2 before login and 1 after, and the dashboard showed 1 person.

The first link winsIf a shared device logs into a second account without reset(), the SDK doesn't link again, and the server ignores later links for the same anonymous id. So one person's history can't move to someone else. The first version stored links in a table type that keeps the newest row after a background merge, which would have silently flipped this to "last link wins". A test now merges the table and checks again.

A retried event counts once

SDKs retry, so the same event can arrive twice. Counts use uniqExact(event_id) rather than count(), and the table merges duplicates over time. A test sends the same event in two separate inserts, like a real retry, and expects it counted once. (Copies in one insert are merged right away, which first made that test pass for the wrong reason.)

Days in UTC, on any server

Charts group by hour, day or week in UTC. The first run returned an empty chart: ClickHouse converts dates in the server's timezone, and this machine is on UTC+1, so every day started at 23:00 the day before and matched nothing. Every query now runs with session_timezone=UTC. CI runs in UTC, so this would have passed there and broken on the first server in another timezone.

Errors come first

The SDK queue keeps up to 1,000 analytics events but counts them separately from errors (100), so a burst of tracking can never push a crash report out. On the server, analytics never touches issues: an event can't become an issue even if it carries an exception. Analytics also has its own queue on disk, so a ClickHouse outage's worth of clicks can't take the space errors need.

Acknowledged only after ClickHouse has it

Events used to leave the durable queue when they reached the writer's memory, then wait for the next insert. A kill -9 under load lost 1,987 of 52,360 accepted events, and all of them when ClickHouse was also down. Now an event stays queued until the insert succeeds. A crash can make the queue deliver some again, which is safe: the table merges rows with the same event_id, and counts use uniqExact(event_id), so a repeat counts once.

When the queue is full, the oldest clicks go

The analytics queue is capped by JUJU_ANALYTICS_QUEUE_MAX_MB (512). Past that, the oldest analytics events are dropped, the opposite of the error queue, which refuses new events so the SDK retries. Nobody should be turned away over counting clicks while ClickHouse is down.

One bad row can't block the rest

With durable delivery, a row ClickHouse always refuses would come back forever and hold up everything behind it. When ClickHouse answers "bad data" (HTTP 400), the writer halves the batch until the row is alone, writes the rest, and keeps that row in the dead-letter stream for a week. Any other failure is treated as temporary and retried for as long as it takes.

Values go in as parameters

Event names, property keys and dates are sent to ClickHouse as query parameters ({event:String}), never pasted into SQL. A test tries names like x' OR 1=1 -- and '; DROP TABLE events; --. They match nothing, and the table is still there.

Using it

Send events, then read them

// web and React Native
juju.capture("checkout_started", { plan: "pro", items: 3 });
juju.identify(user.id);   // after login
juju.reset();             // after logout

// Flutter
Juju.capture('checkout_started', {'plan': 'pro', 'items': 3});
Juju.identify(user.id);
Juju.reset();
# run it locally: ClickHouse without Docker (a pinned, checksum-checked build)
make devch
JUJU_CLICKHOUSE_URL=http://127.0.0.1:8123 make dev

# on a VPS, deploy/setup.sh installs the same ClickHouse version and turns analytics on

The dashboard's Analytics page (g a) has three tabs. Trends counts an event or the people who did it, over 24 hours to 90 days, broken down by platform, OS, browser, release, environment or any property. Funnels shows how many people did steps in order within a time window. Retention shows how many came back on each following day. Every choice is in the URL, so a chart can be shared.

What testing exposed

empty charts off UTC

ClickHouse used the server's timezone for days. Every query now runs in UTC.

analytics never set up

Creating the database named the database being created, which doesn't exist yet. It now runs in default.

last login would win

A table type that keeps the newest row would have moved history after a merge. Links now keep the first.

test servers left running

ClickHouse's watchdog forks the real server, so stopping one process left it running and the test run hung. Tests now stop the whole process group.

axis labels overlapping

On a phone, the last two dates ran into each other. A label too close to the last one is now skipped.

accepted events lost in a crash

Events were acknowledged on reaching memory, not ClickHouse. They now stay queued until the insert succeeds.

lowering a limit stopped the server

Reducing a queue limit made the storage budget smaller than what existing streams had reserved, so juju wouldn't start. The budget is now only a ceiling; each stream's limit is the real one.

a test that asserted a bug

A trends test expected a People total of 4 for a, b, a, c, who are 3 people. The headline added up per-day unique counts. The server now counts a true total.

a checksum that couldn't match

The macOS binary unpacks itself on first run, so its checksum changes. The pinned checksum is now taken from the download.

Limits

Not covered yet

  • No person profiles. identify links ids but doesn't store traits like plan or email per person yet. Properties live on events.
  • No filters. Trends break down by one property but can't filter ("only plan = pro") yet.
  • Retention is daily, for people whose first starting event falls in the range, and counts a return on each later day. No weekly view yet.
  • Funnels and retention use the time window you choose, not someone's full history before it.
  • Limited timezone choice. Charts are always in UTC, and the page says so.
  • A very long outage drops the oldest events, without a log line. Past JUJU_ANALYTICS_QUEUE_MAX_MB, JetStream removes them itself. juju logs how many are waiting when it stops and every failed write, but not a count of those dropped.
  • Redelivery after a crash takes up to 60 s. Events a crashed process held come back once their acknowledgement time runs out, so charts can lag by that long after a kill -9. A clean stop has no such wait.
  • Untested on a real VPS. deploy/setup.sh installs ClickHouse 26.8.18.2 from its apt repository with a memory cap. The settings were checked against the real binary, but the install hasn't run on a real VPS yet.
