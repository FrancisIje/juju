juju roadmap

Architecture

How the pieces fit

An app with a juju SDK catches an error, packages it as a JSON event and sends it to the ingest endpoint. Ingest answers fast and hands the event to a worker. The worker groups it into an issue, turns minified stack traces back into readable ones, and stores it. The dashboard reads from storage.

Decisions

Key choices and why

One Go binary first, split later

juju serve runs ingest, API and worker in one process. Each lives in its own package, so you can split them into separate services later.

Why: with one binary there is one thing to run and debug while you learn. The package boundaries keep the option to scale ingest separately when traffic needs it.

Postgres only, until analytics

Store projects, issues and events in Postgres. Add ClickHouse in phase 7.

Why: error volume is small at first, and Postgres handles it well. ClickHouse is a columnar database built for "count events by X over time" queries, which is the analytics workload. Adding it before you need it means two databases to operate.

Standard library first

net/http with Go 1.22+ routing patterns, log/slog, pgx for Postgres, goose for migrations.

Why: modern Go's standard router handles POST /api/v1/projects/{id}/events directly. Fewer frameworks means you learn Go itself, and there is less to upgrade.

One event format for every SDK

A versioned JSON envelope (v1) that all three SDKs send. The server only knows this format.

Why: the contract between SDKs and server is the most expensive thing to change later, because old app versions stay in the wild for years. Versioning it lets v2 come later without breaking them.

Shared TypeScript core

@juju/core holds the queue, transport, breadcrumbs and event building. The web and React Native SDKs are thin layers over it.

Why: both run JavaScript. Fixing a retry bug once fixes it everywhere. Flutter needs its own Dart SDK, but it copies the same design.

Accept fast, process later

Ingest validates, answers 202 Accepted, and queues the event. A worker does the slow work.

Why: an SDK request must never slow down or crash the host app. The queue also absorbs spikes, such as one bad release crashing every user at once.

Phases

What to build, in order

Each phase ends with something you can run and see. "Done when" is checked with the /verify skill: tests plus a manual run against the real system.

Phase 0

Foundations

Done
  • git init, monorepo folders: server/, sdks/, dashboard/, examples/
  • go mod init in server/, cmd/juju/main.go with a serve subcommand
  • Config from environment variables, slog JSON logging, GET /healthz
  • docker-compose.yml with Postgres, goose migrations, a Makefile (make dev, make test)
  • CI: GitHub Actions running gofmt, go vet, go test -race
Why nowEverything later needs a running server, a database and a test command. Setting up CI on day one means every later change is checked automatically.
Done whenmake dev starts the stack, curl localhost:8080/healthz returns 200, and CI is green.
Phase 1

Error ingestion MVP

Done
  • Tables: organizations, projects (with a public key), issues, events
  • POST /api/v1/projects/{id}/events: key check, 1 MB body limit, gzip support, JSON validation
  • Deduplicate on event_id, because SDKs retry and the same event can arrive twice
  • Fingerprinting: hash of exception type plus normalized in-app frames, giving one issue per fingerprint
  • In-process queue (a buffered channel) between ingest and the worker, replaced by a durable one in Phase 9
  • GET /api/v1/projects/{id}/issues and /issues/{id}/events
Why nowGrouping errors into issues is the core of the product. You can build and test all of it with curl before any SDK exists.
Done whenTwo curl events that differ only in line number land in one issue, a different exception type creates a second issue, and a bad key returns 401.

Web SDK

Done

Phase 5

Symbolication

Done
  • Upload API plus a juju-cli command for source maps (web, React Native) and Dart --split-debug-info symbols
  • The worker rewrites minified or obfuscated frames into real file, line and function before fingerprinting
  • Debug ids: each JavaScript bundle names its own source map (juju sourcemaps inject, withJujuConfig for Metro), so the release name no longer has to match
Why nowProduction stack traces are unreadable without it (a.js:1:48213). It also has to run before fingerprinting, or each build would group errors differently.

See real frames before and after symbolication, and how it was verified →

Done whenA minified web error and an obfuscated Flutter error both show the original source location.

Phase 9

Scale and hardening

Done
  • Replace the in-process channel with NATS JetStream or Redis Streams, so events survive a restart
  • Per-project rate limits, quotas and client-side sampling
  • PII scrubbing (emails, tokens in URLs), data retention jobs
  • Split ingest into its own deployment, plus load testing with k6
Why nowOnly now is there real load to measure. Optimizing earlier would mean guessing.

See what happens when the server dies, the database goes down or a burst arrives, and the numbers →

Done whenIngest keeps p99 under 50 ms at a target rate, and restarting the worker loses no events. Verified: NATS JetStream, embedded in the binary. Killing the server with kill -9 mid-flood lost 0 of 57,700 accepted events, against 4,237 of 60,511 with the old channel. p99 stayed between 1.3 and 21 ms in four runs at 5,000 events/s, and was 15 ms at four times that.
Workflow

How every change gets verified

The project has a /verify skill in .claude/skills/verify/. Run it after any change. It takes these steps:

diffFind what changedMap each changed file to its component and describe the new behaviour in one sentence.
testWrite the testTable-driven Go tests, fuzz tests for parsers, golden files for grouping, and SDK tests.
runRun the checksgofmt, go vet, go test -race, plus the SDK test runners.
curlCheck it by handSend real events, then check the API, the database and the dashboard. Try the failure cases too.
reportExplainWhat changed and why, what was verified, what wasn't, and one concept to learn.
