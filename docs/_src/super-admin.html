juju · Operations · Super admin

See every organization on your server without reading their data

Until now, juju's dashboard only showed the organizations you belonged to. The person running the server had no way to see who had signed up, which projects were sending events, or who was running out of quota. The super admin view answers those questions with counts, and keeps each customer's errors private.

[super admin] VERIFIED real binary, Postgres and Chrome: 6 projects in 5 organizations with the right status; ordinary account got 404; 0 customer strings in admin answers; 25 ms over 1,006 projects and 1,000,232 events
The problem

Operators need the whole picture, and customers need their privacy

Before this change, answering "is Globex over its quota?" meant opening a database shell on the server. The obvious fix, letting an admin open any project, would also let them read every customer's stack traces and error messages. Those can hold personal data, as this real test message shows:

PRIVATE customer text: card declined for jo@acme.test

So the view has a narrower job: show enough to run the server, and nothing from inside a project. In the verification run, that message's project appeared as a row of numbers, and searching every admin answer for the text found nothing.

How it works

Four decisions

The flag is set from the server's shell, never over the web

Being a super admin is a column on the user's row, users.is_superadmin. Only the juju user superadmin command changes it.

An allow-list of emails in the config looks simpler, but juju doesn't verify email addresses when people sign up. Anyone could register the allow-listed address first and become an admin. With no HTTP endpoint for the flag, a web bug or a stolen session can't grant it either.

It's checked on every request, and refusal looks like nothing's there

The flag comes from the same database lookup that checks the session. Ordinary accounts get exactly the same 404 as a route that doesn't exist.

Because nothing caches the flag, a revoke applies to the admin's very next request, even with a session still open. The sidebar link is hidden too, but that's only tidiness: the server's check is what protects the data.

Counts and contacts only

Super admins seeSuper admins don't see
Organization and project names, creation datesIssue titles, stack traces, event payloads
Member emails, names and rolesPublic keys, secret keys, webhook URLs
Event, error, session and unresolved issue counts, quota useAny project page, unless they belong to its organization

Member emails are shown because someone has to be contacted when a project has a problem. Every access is also logged as super admin access with the user id and path, because this view crosses every organization's boundary.

"Last event" comes from a counter ingest already writes

The obvious source, issues.last_seen, misses analytics and session events, which never create an issue, and it uses the app's clock. So project_usage gained last_accepted_at, written with the event counts ingest already saves in batches every few seconds.

That covers every kind of event, uses the server's clock and adds no work per event. Older events have no such time, so issues.last_seen remains a fallback, capped at the current time in case a device's clock is wrong.

What each status means

StatusMeaning
Over quotaUsed its monthly quota, so ingest answers 429. A quota change reaches ingest within 30 seconds.

Using it

Make your account a super admin

The account must exist first. On a server installed with deploy/setup.sh:

# grant, then list who has it
juju-admin user superadmin -email you@example.com

# list only
juju-admin user superadmin

# take it away, effective on the next request
juju-admin user superadmin -email you@example.com -revoke

Reload the dashboard and Super admin appears in the sidebar, at /admin. Search and status filters live in the URL, so you can share a view with another admin. / focuses the search, and ⌘K reaches both tabs.

Bugs this exposed

LEAST ignores NULL

Projects that had never sent anything showed as Active, last event "just now", because Postgres's LEAST(NULL, now) returns now. On the real binary: shop-ios active became shop-ios no_events.

A test that couldn't fail

Removing the last_accepted_at write left the tests green, because the project in the test also had an error to fall back on. A new test uses a project with usage and no issues, and catches both the insert and update paths.

Screens the numbers missed

At 1360 px the Last event column was cut off and the status filter stretched across the page. Both showed up only in the screenshots, so the check now measures the table too.

Limits

What this doesn't do yet

  • It's read-only: changing a quota or suspending an organization still happens from the shell or isn't possible.
  • There's no two-factor login. A stolen super admin password exposes every customer's member emails, so use a strong, unique one and keep the number of admins small.
  • The access record is a server log line, not a page, so reading it takes server access.
  • The page loads all projects at once. That's fast at a thousand projects, but would need paging at many thousands.
  • Event counts run a few seconds behind ingest. Events that arrived before this deploy have no recorded time, so a project that only sends analytics or sessions shows as Quiet until its next event.
  • "Quiet" means nothing arrived. It can't tell a broken SDK from an app nobody opened this week.
