Sessions

A crash-free rate needs one row per session

A session is one run of the app in the foreground on mobile, or one page load on the web. The SDK sends an update when it starts, when it ends, and when it crashes. A release's crash-free sessions is the share of its sessions that didn't end in a crash. It's the number mobile teams watch after every release, because an error count can't tell "10 crashes for 10 people" from "10 crashes out of a million launches".

Updates don't arrive tidily. A phone offline in the background sends its queue later, a retry resends what may already have arrived, and a crash report from the last launch arrives after this launch's start. So the server keeps one row per session and merges every update into it with three rules:

  • Each update carries seq, a counter the SDK raises with every change. The status comes from the highest seq, so a late update can't undo a newer one.
  • Crashed is final. Nothing after a crash makes the session healthy again.
  • Error counts only grow, and the start is the earliest seen. A repeat changes nothing.

The row the server keeps

Why not count sessions per hourCounters are smaller, but a session changes state after it's counted. Moving one from "ok" to "crashed" means knowing it was counted as ok, and a retried update would be counted twice. A row keyed by the session's id absorbs both for free. It's one INSERT … ON CONFLICT DO UPDATE, and the integration test sends the same updates in four orders and expects the same row each time.

A browser tab keeps running after an uncaught error, but something the person was doing broke, so on the web it counts as a crash. The same error object reported twice (caught, then rethrown) is still one error, but if the rethrow crashes the app, the session still ends crashed. A test covers exactly that.

Mobile: the background isn't the end

The OS can kill a backgrounded app without warning, so the SDK sends the session as ended the moment the app goes to the background. If the person comes back within 30 seconds, after glancing at a message say, the same session continues with a higher seq. Later than that, a new one starts. On the Android emulator, pressing Home and coming back 3 s later gave session bb644660 the updates 0 ok → 1 exited → 2 ok, and no new session.

While offline, only the latest update of each session waits in the queue. An app switched away from fifty times on a plane sends one update when it lands, not fifty.

Transactions

Time what people wait for, then show where the time went

A transaction is one thing a person waits for: a page load, an app start, a screen opening. Spans are the steps inside it, like an HTTP request or a script download. A slow transaction then shows its own reason: in the screenshot above, the checkout page took 1.75 s because GET /api/cart took 1.23 s and then failed with a 503.

When is a screen "loaded"?

Most screens finish loading when their data arrives, not when they first draw. So page loads, route changes and screen loads are idle transactions. They stay open while requests are in flight and close once nothing has happened for 1 second. Their end is the moment the last request finished, not when the timer noticed. A transaction still open after 30 s ends as "Timed out", and requests that never answered are marked "Never finished" instead of passing for fast ones.

Why ids become ":id"Every order page would otherwise be its own transaction, seen once, and a percentile over one sample means nothing. Numbers, UUIDs and long tokens with digits in a path segment become :id; words like how-we-grew-a-garden stay.

App start, measured from as early as each platform allows

Every app start records where it was measured from, so two numbers measured from different points never get compared by mistake. Each platform gives something different, and each one was checked on a device:

  • Flutter on Android: from the process start. Dart reads it from /proc/self/stat, with no plugin. Android's own count (am start -W) came out 100–150 ms higher on three cold starts (1357 vs 1257, 1127 vs 1020, 1510 vs 1362 ms), because Android starts timing at the launch request, before the process exists.
  • React Native on iOS: from the JavaScript runtime's start. React Native's "start time" there is the runtime's start, not the app's, so it isn't called a native start.
  • React Native on Android and Flutter on iOS: from init. React Native 0.87 reported no startup times on Android, and iOS has no /proc. Call init first thing for these numbers to mean much.
Why percentiles, not the averageOne 30-second outlier drags an average far away from what most people saw. p50 is the typical wait, and p95 is what the slowest 1 in 20 get, which is usually where the complaints come from.
Why Postgres, for nowThe roadmap puts transactions next to analytics in ClickHouse (Phase 7). This phase shipped first, so it stores both kinds of data in Postgres. Every query reads one project's time window through an index on (project_id, started_at), and percentiles come from percentile_cont. That's fine at today's volume, and moving to a columnar store later changes the store, not the wire format or the SDKs.
Using it

Update the SDK. That's mostly it

Sessions and timing are on by default. These are the lines that matter beyond init:

// Web: nothing more. Optional: send a quarter of page loads, time your own work
juju.init({ dsn, release: "web@2.3.1", tracesSampleRate: 0.25 });
const tx = juju.startTransaction({ name: "checkout" });
const span = tx.startChild({ op: "db", description: "save order" });
span.finish(); tx.finish();

// React Native: init at the top of index.js; screen loads come from navigation
<NavigationContainer ref={ref} onReady={() => juju.trackNavigation(ref)}>
juju.appStarted(); // only without React Navigation: the first screen is ready

// Flutter: the observer times screens; this client times their requests
MaterialApp(navigatorObservers: [Juju.navigatorObserver])
final api = Juju.httpClient();

// Turn either off
init({ dsn, sessions: false, tracing: false })

On the server, nothing to configure: the migration adds two tables, app_sessions and transactions, and both new event types use the same endpoint and key as errors.

What the devices exposed

Android blocks /proc/uptime

The first Flutter app start read the boot clock from /proc/uptime, and passed every test on a Mac. On Android, SELinux denies it to apps, so every start fell back to init. Now a tiny child process supplies "now" on the same clock, and the same launch reports from_process_start.

"native start" that wasn't

On iOS, React Native's start time is the runtime's start, 3 µs from it. The SDK called that a native start and hid the native part. It now says from_runtime_start, and the real values are a test.

158 ms nobody could explain

Chrome page loads had a gap before the first step. The raw timings showed the request waiting after the connection was ready. It's now its own step, "Queued in the browser".

"GET ../../Makefile"

Spans showed URLs as written in code. After a route change those point somewhere else; this one was really /examples/Makefile, hence its 404. Spans now show the resolved path.

stale SDK in the example app

make example-rn-deps kept the old SDK when the version number hadn't changed, so a device test could run old code. It now installs the new packages by name.

"1.01 / s" on phones

Numbers split from their units and versions broke mid-number (web@1.0. / 1). Both stay on one line now. The waterfall moved above the sample list, where a phone reaches it.

Limits

Not covered yet

  • Native crashes (a crash in Swift, Kotlin or C++) and a phone killing the app for memory leave no report, so those sessions stay "ok" and count as crash-free. Catching them needs native code in the SDKs.
  • App start on iOS and React Native Android starts at the JavaScript runtime or at init, not at the tap on the icon. A native module could record the earlier moment.
  • Sampling is a fixed share per SDK (tracesSampleRate). There are no server-side quotas yet; that's Phase 9.
  • Storage is Postgres with no retention job yet, so rows accumulate. Moving transactions to ClickHouse with Phase 7, plus retention, are the next steps.
  • No alerts on a falling crash-free rate or a slower p95 yet, and no release-health API for scripts (to stop a rollout in CI).
  • Session replay (rrweb) from the roadmap isn't started.
