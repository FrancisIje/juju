Crash reports that outlive the app

On a phone, a fatal JavaScript error ends the app. The crash is the error you most need to know about, and it happens at the one moment the app can't send anything. This page explains how @juju/react-native keeps that report, and how it was verified on iOS and Android.

The problem

What happens in the milliseconds after a crash

In a release build, React Native's global error handler stops the app as soon as it's called. Anything still waiting to be sent or saved is gone with the process.

Send it and let the app die

  1. 0 msTypeError thrown, nothing catches it
  2. 0 msreport built, send starts
  3. 1 msReact Native's handler runs
  4. 1 msprocess killed (SIGABRT), send cancelled

The crash is never reported. Offline, nothing would have worked anyway.

What juju does

  1. 0 msTypeError thrown; juju's handler sees it first
  2. 0 msreport queued, tagged fatal: true
  3. ≤ 2000 mswait for the save to storage and a send attempt
  4. thenReact Native's handler runs, app closes
  5. next launchsaved report loaded and sent, then removed from storage

The crash arrives once, even if the phone was offline when it happened.

On the Android emulator with the server down, juju handed control back 89 ms after the error: the save finished and the send failed fast, so it didn't need the full 2 seconds.

How it works

Four pieces

1. Wrap the global handler, never replace it

React Native has a single global error hook, ErrorUtils.setGlobalHandler. juju installs its own handler and keeps the previous one. Every error is reported, then passed to React Native's handler, so the red error screen in development and the crash in release behave exactly as before.

Why wait at most 2 secondsWaiting gives storage time to finish. A cap keeps a hung disk or network from freezing a crashing app. A second fatal error while waiting goes straight through.

2. Save the queue to the device

Every change to the queue is written to AsyncStorage under @juju/queue. Writes run one after another, so an older snapshot can never overwrite a newer one, and a burst of 50 errors becomes a handful of writes. When the server confirms events, they're removed from storage too.

The race this avoidsAt launch, juju first loads what the last run saved. If an error happened before that load finished, saving the new queue would overwrite the old crash report before anyone read it. So every save waits for the load. A test fails if this rule is removed.

3. Catch promise rejections through Hermes

The global handler never sees a promise that fails with no .catch(). Hermes, React Native's JavaScript engine, reports those through its rejection tracker. juju installs a tracker that reports them, and keeps React Native's "Possible unhandled promise rejection" warning in development.

4. Follow the app's lifecycle

When the app goes to the background, the OS can kill it at any time without warning, so juju saves and tries to send. When it becomes active again, juju retries straight away instead of waiting out the backoff. Each change is also a breadcrumb.

Using it

Setup in an app

import AsyncStorage from "@react-native-async-storage/async-storage";
import * as juju from "@juju/react-native";

juju.init({
  dsn: "https://pk_...@juju.example.com/1",
  release: "shop@1.4.0+12",
  storage: AsyncStorage,   // without it, a crash can be lost
});

// optional: screen changes as breadcrumbs
<NavigationContainer ref={ref} onReady={() => juju.trackNavigation(ref)}>
  • storage is passed in by the app, so the dependency is visible in the app's own code. If it's missing, juju logs a warning at startup.
  • environment defaults to development in debug builds and production in release builds.
  • No native module. Device details come from React Native's built-in Platform and Dimensions, so installing juju needs npm only: no pods to add and no extra native setup.

Shared core

What React Native forced us to change in @juju/core

The core is shared with the web SDK, and some things that work in every browser don't work in React Native.

new URL()

React Native's URL is incomplete: reading url.username throws "not implemented". The DSN is now parsed without it.

TextEncoder

Missing in older React Native. Byte counting for size limits now has a fallback that gives the same answers.

address at …

Hermes writes release frames as at fn (address at index.android.bundle:1:2345). The parser now strips the prefix.

XHR, not fetch

React Native's fetch is built on XMLHttpRequest. Wrapping XHR records each request once. The wrapper moved into core and the web SDK uses it too.

Verification

Tested with release builds, not just tests

Debug builds run differently: they load JavaScript from a development server and show an error screen instead of crashing. So both apps were built in release mode, with JavaScript compiled to Hermes bytecode as in a store build. A crash was triggered with the juju server off, then the app was reopened with the server on.

The automated suite has 112 SDK tests. Two were checked by breaking the code on purpose: removing the crash wait, or the load-before-save rule, makes them fail.

Found on the devices, fixed afterwards

  • Hermes's own InternalBytecode.js frames were counted as app code.
  • Android reported its API level (37) as the OS version. It now reports version: "17" and api_level: 37.
  • Gradle reported a successful build without re-bundling the updated SDK. The bundling step now has to be forced to rerun, and the APK's contents checked.
Limits

Not covered yet

  • One bug, two issues. The same crash on iOS and Android groups separately, because the bundle file names differ (main.jsbundle, index.android.bundle). Source maps in Phase 5 turn frames into real files like App.tsx, which match on both.
  • App code vs React Native code. In a release build everything is in one bundle, so frames from React Native itself still count as app code until Phase 5.
  • Native crashes in Swift, Objective-C, Kotlin or Java aren't caught. They need a native module, planned for later.
  • Physical phones weren't tested, only the simulator and the emulator.
