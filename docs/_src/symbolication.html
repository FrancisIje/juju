    JavaScript

    Source maps: web and React Native

    A source map records, for each position in the minified file, the original file and position it came from. Frames are matched to uploaded maps by release and bundle file name (app.min.js, index.android.bundle).

    Columns are counted differently

    Browsers and Hermes report columns starting at 1; source maps count from 0. Off by one usually still lands inside the same token, which hides the bug, so a test uses a map where neighbouring columns come from different lines.

    Function names take two tricks

    A source map maps positions, not "which function am I in". juju recovers the name in two ways:

    1. The caller's call site. The frame below is paused on the call into this function, and the map's original identifier there is the function's real name (cartTotal in cartTotal(cart)).
    2. The original source. When the caller is native code (like Array.map), read the original file upward, counting braces, to the enclosing function or const name = () =>.

    React Native release builds run Hermes bytecode, where a frame's "column" is a bytecode offset (1:436611). The release build's composed source map translates those too. Once frames point at real files, node_modules code is no longer counted as app code.

    Dart

    DWARF: Flutter's obfuscated builds

    With --split-debug-info, Flutter prints build_id and addresses like _kDartIsolateSnapshotInstructions+0xbc357. The saved symbols file holds DWARF, the standard format that maps machine-code addresses to functions and lines. It's ELF for Android and Mach-O for iOS; Go's standard library reads both.

    Return addresses point after the call

    Every frame except the top one holds the address execution will return to: the instruction after the call. When the call ends a line, that address already belongs to the next line. Looking up address − 1 lands on the call itself.

    0x101cb
    line 173: the code just before, where address − 1 lands (for a real return address, the call)
    0x101cc
    line 163: where a new line's code starts

    A line boundary in the real macOS debug file, used by the test suite: it treats 0x101cc as a return address and expects line 173. With the −1 removed, the test fails with "return address 0x101cc: line 163, want the call's line 173".

    Matching Dart's own decoder

    • Inlined functions share one address, so one raw frame can become several. CartPage.build was inlined into checkout in the test build.
    • Compiler helpers (closure call stubs, a function "inlined into itself") are marked artificial in DWARF and hidden.
    • Exact output. For two real debug files, macOS and an obfuscated Flutter Android build, juju's frames match package:native_stack_traces frame for frame.
    Using it

    Upload after each release build

    export JUJU_URL=https://juju.example.com JUJU_PROJECT=1 JUJU_SECRET_KEY=sk_...

# web: the *.map files next to your bundles
juju upload -kind sourcemap -release web@2.3.1 dist/

# React Native (Android): the composed Hermes map from the release build
juju upload -kind sourcemap -release shop@1.4.0+12 \
  android/app/build/generated/sourcemaps/react/release/index.android.bundle.map

# Flutter: flutter build apk --release --obfuscate --split-debug-info=build/symbols
juju upload -kind dart_symbols build/symbols/
    • The release must match what the SDK sends. Dart symbols are matched by build id instead, which the server reads from the file.
    • The secret key is required: these files contain your source code.
    • Upload before the release ships. Events that arrive before their file aren't reprocessed later.

    What real files exposed

    tests that couldn't fail

    Breaking the column conversion or the −1 rule left the tests passing. New tests now target those edges.

    lines missing on Android

    The Android file's line table is out of address order, and a reused line reader gave up. Shared between workers, it was also a data race.

    raw helper frames

    Addresses made only of compiler helpers stayed raw with a misleading note. Now they're hidden, as Dart's decoder does.

    SDK frames as app code

    Dart's debug info names files by path (third_party/dart/sdk/…), not dart:. The app-code check now knows those paths.

    Limits

    Not covered yet

    • Reprocessing. Events received before their debug file stay as they arrived.
    • React Native on iOS needs the source map written during the Xcode build (SOURCEMAP_FILE), so the iOS/Android split for the same bug is only fixed on Android.
    • Obfuscated exception types. Dart core types stay readable, but your own exception classes need the obfuscation map uploaded too.
    • Very large symbol files are read fully into memory: fine at 2 MB, untested past 100 MB.
